## 2026-10-24 · 音区漂移的根因是 `instruct` 为空，不是参考音频或 `spk_emb`

**背景**

短剧项目中出现「同一音色文件合成的多段台词，听感年龄不一致」。以 `voices/柳如烟.wav`
与合成产物 `toonflow_qwen3tts_00004.flac` 做对照，实测中位基频从 318.9 Hz 掉到
174.3 Hz（**-10.46 半音**），频谱质心从 2780 Hz 掉到 1724 Hz（**-38.0%**）。

从合成音频的 FLAC 元数据中解出当时的内嵌工作流，确认 `FB_Qwen3TTSVoiceClone`
**没有传 `instruct` 字段**（缺省为空）。

**决定**

- 把「每次合成都必须把声线卡写进 `instruct`」定为硬性约定；
- `instruct` 的最小有效集是 **音高 + 音色 + 语速** 三项，只写音高不够；
- 不再把「重建参考音频」「调整 `spk_emb`」当作修音色的手段。

**依据（同一音色 / 同一文本 / 同一 seed 42，只改 `instruct`）**

| 组 | instruct | f0 | 相对参考 | 质心 | 相对参考 |
|---|---|---|---|---|---|
| A | 空（复现） | 174.3 Hz | -10.46 半音 | 1724 Hz | -38.0% |
| B | 年龄 + 音高 | 268.5 Hz | -2.98 | 2491 Hz | -10.4% |
| C | 完整声线卡 | **302.7 Hz** | **-0.90** | **2876 Hz** | **+3.5%** |
| D | 只写年龄 | 283.5 Hz | -2.04 | 2248 Hz | -19.1% |
| E | 只写音高 | 297.1 Hz | -1.23 | 2443 Hz | -12.1% |

A 组三项数字与原文件逐位一致，确认该路径是确定性的、seed 可复现。

**影响**

- `instruct` 为空时 `VoiceCloneNode` 会静默降级（`nodes.py:958` 把空串转成 `None`），
  不报错、不告警。这是一个危险的默认行为：用户以为音色已保存，实际每次合成都在自由发挥。
- 仅补音高能把 f0 拉回，但**频谱质心（年龄感）修不回来**（D 组 -19.1%）。只有包含
  语速/口音等完整描述的 C 组能让质心回到 +3.5%。
- 待办（未实施）：给 `VoiceCloneNode` 增加「已连 `voice_clone_prompt` 但 `instruct`
  为空」的告警。仅改日志，不改行为。

## 2026-10-24 · `spk_emb` 是声纹锚点，不能用作风格旋钮

**背景**

排查音色漂移时，需要判断 `ref_spk_embedding` 能否用于「调整音色」（例如更年轻、更亮）。

**决定**

- `spk_emb` 只用于**测量**（余弦相似度判断是否同一说话人），不用于**编辑**；
- 音色的可控调节通道是 `instruct`，其次是更换参考音频，再次是微调模型。

**依据**

- `spk_emb` 由 ECAPA-TDNN 产出（`qwen3_tts_model.py:347` 注释引用声纹识别论文），
  判别式训练目标是「区分说话人」，2048 个维度**没有语义坐标**，不存在「往某方向走 = 更年轻」。
- 注入方式是把整向量当作一个 token 位置拼进序列（`modeling_qwen3_tts.py:2210`）：
  `speaker_embed.view(1, 1, -1)`。技术上扰动会生效，但结果不可控。
- 实测反证：A 组与 C 组的 `spk_emb` **完全相同**（同一个 `.qvp`），输出 f0 却相差近一个八度。
  说明 `spk_emb` 锁得住「是谁」（MFCC 相似度 0.98），**锁不住音区与年龄感**。

**影响**

- 结论：`spk_emb` 是「同一个人」的**必要不充分条件**。
- 节点层从未暴露 `spk_emb` 编辑入口（`nodes.py` 中无相关代码），也不建议新增。

## 2026-10-24 · 参考音频长度不是音色稳定性的瓶颈（证伪）

**背景**

曾假设「参考音频只有 2.5 秒导致 ICL 前缀信息不足，进而音色漂移」，并计划据此重建音色。

**决定**

- 撤回该假设。参考音频长度可以恢复到官方建议的 5–15 秒，但**不应作为解决漂移的手段**；
- 不在音色诊断工具中把「参考音频过短」标为高优先级问题。

**依据（同源音色，唯一变量是长度）**

用 `VoiceDesign` 生成一段 8.86 秒连贯语音，再用 `TrimAudioDuration` 截出前 2.5 秒，
分别建 ICL 音色，各跑 5 个 seed：

| 组 | 参考长度 | f0 CV | 质心 CV | 组内 MFCC 相似度 |
|---|---|---|---|---|
| long | 8.86 s | 5.0% | 5.6% | 0.9979 |
| short | 2.5 s | 4.2% | 6.2% | 0.9982 |

**影响**

- 跨组 MFCC 相似度 0.9971，与源音频相似度都在 0.994 以上，差异在噪声范围内。
- 「8–15 秒」是官方对克隆质量的通用建议，不是稳定性修复手段。

## 2026-10-24 · 新增音色库诊断工具 `tools/inspect_voices.py`

**背景**

音色库中混有大量测试残留，且存在两类静默失败：`SaveVoice` 漏接 `audio` 只写
`.qvp`/`.json`（`LoadSpeaker` 靠 wav 定位，于是音色不可加载）；`.qvp` 可能是
x-vector-only 模式，相似度上限被砍。

**决定**

- 新增 `tools/inspect_voices.py`，扫描音色库并输出：加载可行性、克隆模式（ICL/xvec）、
  参考音频实际时长、`ref_text` 字符数、字符/秒密度、以及逐项判定；
- 目录发现复用 `voice_store.py` 的 `collect_voice_dirs`，保证与 ComfyUI 节点所见一致；
- 时长探测优先用标准库 `wave`（零依赖），非 WAV 才回退 `soundfile`；
- 读取 `.qvp` 时用同名占位类喂给 unpickler，避免导入 `qwen_tts`（省去 transformers 加载）。

**影响**

- 输出列：`voice / wav / qvp / json / mode / secs / chars / c/s / verdict`。
- 判定阈值：`< 4.0s` 为 VERY SHORT；`4.0–5.0s` 为 short；中文 `c/s > 8.5` 或
  拉丁 `> 4.5` 判为文本与录音不匹配；中文 `< 3.0` 或拉丁 `< 1.5` 判为 ref_text 不完整。
- 配套 `tests/test_inspect_voices.py`（33 个用例），其中
  `test_verdict_and_notes_agree` 断言「verbose 有告警」与「verdict 非 ok」永远一致。

## 2026-10-24 · 内联标签体系是本仓库自造，与官方 Qwen3-TTS 无关

**背景**

有说法称「官方 Qwen3-TTS 有 `[sad]` `[whispering]` `[sighing]` 等内联标签，
信息分散在文档、指南和代码中」。

**决定**

- 明确：开源 Qwen3-TTS 的**唯一**风格控制通道是 `instruct` 自然语言文本，不存在标签层；
- 本仓库 `EmotionalTTSNode` 的 `[sad]` / `[pause:800ms]` / `[rate:1.2]` 由
  `emotion_utils.parse_rich_text` 在调用模型前解析，模型本身看不到这些标签；
- 文档与对外说明中不得把第三方站点的标签表描述为官方能力。

**依据**

- 官方仓库全树 65 个文件，无 `markup.md`、无任何 `.h` 文件（`qwen_tts_compose.h` 不存在）；
- `_build_assistant_text`（`qwen3_tts_model.py:269`）把文本原样拼进对话模板，
  没有任何标签分词或映射逻辑；
- 那套标签属于 **Qwen-Audio-TTS**（DashScope 商用 API），与开源 Qwen3-TTS 是两条产品线；
  相关第三方站点 qwen3tts.net 页脚声明「not affiliated with Alibaba Group, Qwen, or Tongyi」。

**影响**

- 标签写错（如 `[laugh]`）不会报错，会被当作字面文本送进模型，存在被念出来的风险。
- 官方 `Instruction Control` 列显示 0.6B CustomVoice 不支持 instruct，与节点中的硬报错
  （`nodes.py:1184`）一致。

## 2026-10-24 · 实验方法约束：禁止用拼接音频扩展参考样本

**背景**

首次尝试验证「参考音频长度影响」时，把 2.5 秒音频拼接 4 份凑成 10.1 秒。该做法被指出
会造出「同一句话连续重复 4 遍」的伪韵律，属于分布外（OOD）输入——模型会去建模重复模式，
而非说话人特征，结论不可外推。

**决定**

- 凡是改变参考音频长度的实验，必须**从同一段连贯录音截取**，不得拼接；
- 比较不同条件时，被测音频必须同文本、同情感、同 seed，且指标要能隔离文本韵律的影响。

**依据**

- f0 中位数**跨文本不可比**：同一音色读陈述句与反问句，f0 天然相差 20–60 Hz；
- 早期「用 4 段不同情感的 f0 计算段内离散度」的方法同样失效——31.9% vs 31.7% 混入情感变量，
  两个数字都没有意义。

**影响**

- 后续所有音色实验改用「同源音频 + 截取」构造对照组。
- 评估听感与音色时，`f0` 只用于同文本对比；跨文本比较须改用与内容无关的指标
  （频谱质心、`spk_emb` 距离）。

## 2026-10-24 · 标签体系升级：`[style:]` 自由文本、未知标签剥离、统一停顿语法

**背景**

内联标签是本仓库自建的 DSL（模型只接受 `instruct` 自然语言），不是模型能力。
原实现有三个问题：未识别的标签会原样进入文本、可能被模型念出来；预设表固定，
无法表达长尾风格；`EmotionalTTS` 用 `[pause:800ms]`、`DialogueInference` 用
`[break=0.5]`，两套语法互不通用。

关键判断：既然 `instruct` 接受任意自然语言，**用户没被预定义的标签，其内容本身
就可以直接当 instruct 用**，无需扩表。

**决定**

1. 新增 `[style:任意文本]`（别名 `[instruct:...]`），括号内文字直接并入该段
   `instruct`，不做查表。与 `[sad]` 等预设可叠加，顺序为 预设 → style → 节点级 instruct。
2. 未知标签**默认剥离**，并记录到 `RichSegment.dropped_tags` 供调用方提示；
   `preserve_unknown_tags=True` 恢复旧的「原样保留」行为。
3. `[break=0.5]` **废弃**：显式识别后剥离，并提示改用 `[pause:...]`。
   即使开启 `preserve_unknown_tags` 也不保留——留着只会被念出来。
4. 裸标签允许空格（最多 4 段词），但仍必须以 `EMOTION_ALIASES` 精确命中才算识别。
5. `[emotion:xxx]` 命中失败时不再原样保留，而是作为 style 文本使用——
   显式写了 `emotion:` 说明用户本意就是设定情感。
6. 模块加载时校验别名表：alias 的 value 必须是已知预设、不得遮蔽预设名、
   `EMOTION_CHOICES` 不得重复。
7. `DialogueInferenceNode` 接入同一套标签。新增 `expand_dialogue_line()`：
   先按标点切分（保留原有停顿节奏），再对每个片段解析标记。
   `instruct` 由单值改为**按片段传列表**，模型接口已支持
   （`qwen3_tts_model.py:604` 按 index 取值）。

**影响**

- **解决了「多角色」与「情感」互斥**：一个角色可以在一行内切换情感，音色不变。
  不再需要「多角色节点 + 单音色情感节点」二选一。
- **破坏性变更**：`[break=0.5]` 失效；未知标签从「保留」变为「剥离」。
  含 `[break=]` 的旧脚本需要改为 `[pause:]`，否则停顿会消失（会在日志中提示）。
- `[style:]` 是粘滞的，与 `[sad]` 一样持续到下一个标签，不切分段。
  只有情感/停顿/语速标签会 flush 出新段。
- 测试：`tests/test_emotion_utils.py` 增至 43 例，新增
  `tests/test_dialogue_markup.py`（13 例）覆盖 Dialogue 的片段级标记。
- 文档：中英文 README 同步更新标记表、未知标签策略、废弃说明，
  并补充 Dialogue 支持内联标记的说明。

**未实施**

- `EmotionalTTSNode` 与 `DialogueInferenceNode` 仍各自保留 `preserve_unknown_tags`
  的内部默认（`False`），尚未暴露为节点开关。
- 段间交叉淡化 / 响度归一化（原计划批次 3）未做。

## 2026-10-24 · 段间交叉淡化与响度归一化取消（实测证伪）

**背景**

原修改计划「批次 3」准备给段间拼接加 20ms 交叉淡化与峰值归一化，理由是代码层面
观察到两处 `torch.cat` 之间没有任何过渡处理。

**决定**

- **取消交叉淡化**；
- **取消响度归一化**；
- 批次 3 整个移除，不再列入待办。

**依据（实测）**

1. **接缝处不存在爆音**。Dailogue 产物（6.83s、2 段）逐样本检查：静音边界跳变
   `0.0006`（约 -60 dB），每段起始样本 `< 0.0012`、结束样本 `< 0.0008`。
   模型生成的音频自带淡入淡出，段尾已自然衰减到近零。

2. **响度差在可闻阈值以下**。

   同音色同文本多 seed / 多 instruct 强度（28 个样本）：

   | 数据组 | 样本数 | RMS 范围 (dBFS) | 跨度 |
   |---|---|---|---|
   | exp5 中性多 seed | 10 | -19.96 ~ -18.10 | 1.86 dB |
   | exp6 instruct 强度 5 档 × 3 seed | 15 | -19.78 ~ -17.97 | 1.81 dB |
   | exp7 VoiceDesign | 3 | -22.08 ~ -18.54 | 3.53 dB |

   跨情感预设（同音色/同文本/seed 42，7 个预设）：

   | preset | RMS dBFS | 相对 none | peak dBFS |
   |---|---|---|---|
   | none | -19.28 | — | -5.00 |
   | whisper | -19.14 | +0.14 | -4.25 |
   | calm | -20.13 | -0.85 | -3.97 |
   | sad | -18.89 | +0.39 | -3.61 |
   | angry | -19.00 | +0.28 | -4.30 |
   | excited | -19.70 | -0.43 | -4.53 |
   | weak | -19.30 | -0.02 | -4.94 |

   RMS 跨度 **1.24 dB**（声压 1.15 倍），peak 跨度 1.39 dB。人耳约 3 dB 才明显。
   注意 `whisper` 与 `angry` 的 RMS 几乎相同（差 0.14 dB）——模型表达「耳语」靠的是
   气声比例与频谱，不是降低音量。

**方法论教训**

最初用一个 2 段的样本得出「0.4 dB，不存在」，被指出样本量不足。补测到 7 个预设
与 28 个同级样本后才确认结论一致。**凡是"不存在"的结论，样本量必须足够，
且要覆盖极端条件（如 whisper/angry），不能靠单例。**

**影响**

- 「自造段间后处理」这类改动，必须先实测目标问题是否存在，不能只凭代码观察立项。
- 保留：`EmotionalTTS` 插静音用 `torch.zeros()`（默认 CPU）而 `Dialogue` 用
  `waveform.new_zeros()`（跟随设备）。前者在 GPU 上多一次拷贝，属性能小问题，
  不影响输出，暂不处理。

## 2026-10-24 · 情感预设与音高的关系不可靠

**背景**

测量跨情感响度时顺带记录 f0，发现预设语义与音高变化方向不一致。

**依据**（同音色/同文本/seed 42，文本为两个反问句）

| preset | f0 (Hz) | 相对 none |
|---|---|---|
| sad | 372.7 | +39% |
| calm | 345.5 | +29% |
| angry | 344.8 | +28% |
| weak | 335.8 | +25% |
| whisper | 286.3 | +7% |
| none | 268.7 | — |
| excited | 267.6 | -0.4% |

`sad` 的预设文案是「低沉悲伤，语气沉重，语速缓慢」，但实测 f0 反而最高。

**决定**

- 不把 f0 作为衡量预设是否生效的依据；
- 情感预设的效果必须靠人耳验收，不能用单一声学指标推断；
- 该组数据本身有混杂因素（文本是两个反问句，句尾升调），不能据此判断
  模型「遵循度低」，只能说明**指令语义与声学参数不是一一映射**。

**影响**

- 之前「补 instruct 把 f0 从 174 拉回 303」的结论仍然成立（那是同一文本、同一句型的
  对照，A 组与 C 组文本一致），但**不应用它推断"instruct 可精确控制音高"**。
- 选择情感预设时应以试听为准，`steer_weight` 与预设文案都是软约束。

## 2026-10-24 · 降低 temperature 无法改善音色稳定性（实测证伪）

**背景**

在排查「多段拼接后音色漂移」时，曾提出「降低 temperature 压缩采样方差」作为候选手段，
并预期 T 从 0.9 降到 0.3 能显著收窄音高波动。

**决定**

- 撤回该建议。**temperature 不作为音色稳定性的调节手段**；
- 「减少切段」也已于同日实验否证，见下一条记录。

**依据**（同音色 / 同文本 / 同 instruct，T × 4 seed = 12 个样本）

| T | f0 均值 (Hz) | f0 std | **f0 CV** | 质心 CV | 组内 MFCC 相似度 |
|---|---|---|---|---|---|
| 0.9 | 308.6 | 30.96 | **10.03%** | 2.51% | 0.9968 |
| 0.6 | 309.2 | 31.98 | **10.34%** | 4.36% | 0.9971 |
| 0.3 | 297.3 | 29.39 | **9.88%** | 5.68% | 0.9965 |

f0 变异系数在 9.88%–10.34% 之间，三档几乎相同；质心 CV 反而随 temperature 降低而
上升（2.51% → 5.68%），与预期方向相反。

**解读**

`temperature` 作用于 codec token 的采样分布尾部，而音高由模型对
`spk_emb` + `ref_code` + 文本的条件估计决定。当条件明确（同音色、同文本）时，
降温度只改变「候选 token 之间的选择概率」，不改变模型对音区的整体判断。
因此 f0 的方差来自**条件估计本身不稳定**，不是采样噪声。

旁证：`exp6` 的 `none` 组（temperature 同为 0.9）三个 seed 的 f0 跨度仅 4.2 Hz（2.3%），
而本组约 10%。差别在文本长度与 instruct 复杂度，进一步说明方差主要由
「文本 + 指令组合」主导。

**影响**

- 不要再把「调低 temperature」当作多段一致性的解法。它的代价是语调变平、表现力下降，
  而收益在实测中为零。
- 累积的「看起来合理但实测无效」的手段已达三项：交叉淡化、batch_size=1、降低 temperature。
  **凡属「后处理/采样参数」层面的音色修复，立项前必须先跑对照实验。**

## 2026-10-25 · 「减少切段可改善音色稳定性」被否证；同时纠正 f0 统计方法

**背景**

在 temperature 实验之后，曾提出「减少切段次数」是唯一确定有效的音色稳定手段，
依据是一组「EmotionalTTS 整句（1 段）」vs「Dialogue 按句号切（3 段）」的对比，
当时得出跨 seed f0 CV 为 3.32% vs 6.60%，差异约 2 倍。

随后又做了第三组「Dialogue 但 period_pause=0（合为 1 段）」，预期 CV 回到 3% 附近，
实测却是 9.61%，与预期相反。

**发现的方法论错误**

前述 3.32% / 6.60% / 9.61% 三个数字**不可比**，原因是：

1. **「整段 f0 中位数」是有偏指标**。三段文本本身音高不同
   （第一句 ~300 Hz、第二句 ~220 Hz、第三句 ~300 Hz，由文本语调决定），
   整段取中位数只落在中间句附近，把真实变异抹平。
   该指标给出的 CV 既低估真实波动，又对分组方式敏感。

2. **各组「自动段数」不同**：`dialogue` 组实测 3–4 段时间歇，`single` 组 3 段，
   段边界不一致时用同一个统计量比较没有意义。

3. 比对 MFCC 时用「整段均值」对「短语」，粒度不对等，整段均值天然更平滑。

**重测（同粒度：短语 vs 短语）**

| 组 | 句内（同 seed 不同句） | 跨 seed（同句位） | 差 |
|---|---|---|---|
| single (EmotionalTTS) | 0.9842 | 0.9945 | +0.0103 |
| dlg pause=0.4（切 3 段） | 0.9840 | 0.9893 | +0.0053 |
| dlg pause=0（1 段生成） | 0.9843 | 0.9944 | +0.0101 |

帧级 f0 分布（p10 / p50 / p90）：

| 组 | p10 | p50 | p90 |
|---|---|---|---|
| single | 173 | 296 | 428 |
| dlg pause=0.4 | 177 | 314 | 443 |
| dlg pause=0 | 184 | 307 | 431 |

**决定**

- **撤回「减少切段能改善音色稳定性」这一结论。** 三组的跨 seed 相似度都在
  0.989–0.995，差异（0.005）小于句子之间的相似度差（0.016），属噪声量级。
- **不把切段次数列为音色漂移的成因**。Dialogue 与 EmotionalTTS 在
  「同一角色、同一文本」下的音色一致性没有可测差异。
- **废弃「整段 f0 中位数」作为稳定性指标**。今后比较音色一致性必须：
  1. 用同粒度单元（短语 vs 短语、段 vs 段）比较；
  2. 或直接用帧级 f0 分布（p10/p50/p90）与全段 MFCC 均值；
  3. 并报告各组实际段数，避免段边界不一致的假比较。

**解读**

组内「句内不同句」相似度 0.984 明显低于「跨 seed 同句位」的 0.994，
说明**同一段音频内部，句子之间的差异远大于多次生成之间的差异**。
换句话说，听感上「这几句不像同一个人」，主要来自**文本内容本身导致的语调差异**，
不是生成不稳定，也不是切段造成的。

这与柳如烟案例并不矛盾：那个案例中 f0 下降了 10 个半音，属于 instruct 缺失导致的
**系统性偏移**，量级远超本次测到的 1–2 个半音的随机波动。

**影响**

- 到此，被实测否证的「音色修复手段」共四项：
  交叉淡化、batch_size=1、降低 temperature、减少切段。
- 唯一确认有效的措施仍是**每次合成传入完整声线卡（instruct）**，
  实测可挽回 9–10 个半音的系统性偏移。
- 对「听起来不像一个人」的排查顺序应改为：
  先看 instruct 是否为空 → 再看文本语调差异 → 随机波动的影响最小。

## 2026-10-26 · 修复 Dialogue 的两个静默失效：`[rate:]` 被丢弃、粘滞状态跨标点丢失

**背景**

用户反馈「Dialogue 为什么不能单独加速，只能整段加速」。排查后发现两个缺陷，
都是引入 `expand_dialogue_line()` 时带入的，且都不会报错、只在听感/行为上偏离预期。

**缺陷一：`[rate:x]` 静默失效**

`expand_dialogue_line` 返回五元组，没有把 `parse_rich_text` 算出的 `plan.rate`
带出来；调用端只能对整段套用节点级 `speed`：

```python
waveform = torch.from_numpy(time_stretch(wav, speed)).float()
```

`[rate:1.5]` 能被正则解析、不报错、不告警，值被丢弃。

**缺陷二：粘滞状态在第一个标点处断掉**

切分顺序是「先按标点切 → 再对每段解析标签」。而 `[sad]` / `[style:]` / `[rate:]`
的粘滞语义依赖 `parse_rich_text` 在一次调用内维持状态。两遍切开后，
第一段之后的片段拿不到状态：

```text
[sad]第一句。第二句。
  → 第一句 instruct='低沉悲伤…'   ✅
  → 第二句 instruct=''            ❌
```

**决定**

1. **调换两遍的顺序**：先 `parse_rich_text` 解析标记（粘滞状态完整），
   再对每段文本调用 `split_text_by_pauses` 切标点。标点停顿语义不变。
2. **元组扩为六项**，末尾加 `rate`；新增 `rates_to_gen` / `chunk_rates`，
   逐片段调用 `time_stretch`。优先级：`[rate:x]` > 节点级 `speed`。
3. `scale_pauses_with_speed` 在 `expand_dialogue_line` 内按片段 rate 生效。
4. 段落级 `leading_pause` 只落在该段第一个片段上，`pause_after` 只落在最后一个片段上，
   避免重复插入静音。
5. `dropped_tags` 每段只上报一次（挂在第一个片段上）。

**影响**

- `[rate:x]` 在 Dialogue 中真正生效，与 `EmotionalTTS` 行为对齐。
- 一行内的 `[sad]` / `[style:]` 现在覆盖整行，直到被下一个标签覆盖——
  这才是文档里一直宣称的「粘滞」语义。
- **行为变更**：此前只有首句带情感的脚本，现在整行都会带。旧脚本若依赖
  「标签只管一句」，需要显式改用 `[none]` 复位。
- 测试：`tests/test_dialogue_markup.py` 13 → 26 例，新增
  `StickyAcrossPunctuationTests`（6 例）与 `PerFragmentRateTests`（7 例）。
- 文档：`README-CHANGE.md` / `README-CHANGE_CN.md` 的解析顺序描述由
  「按标点切分后的片段逐一解析」改为「先解析标记、再按标点切分」，
  并补充 `[rate:x]` 逐片段生效、优先于 `speed`。

## 2026-10-26 · 声线卡合成报错的根因：`unpack_role` 的带卡分支没做单条归一化

**背景**

上一节上线后，用户反馈：`RoleBank` 的 `instruct_{i}` **只要填了值**，
`DialogueInference` 合成就报错；同一工作流把该字段清空则正常。
现象与 `instruct` 文本内容、模型大小（0.6B/1.7B）无关，纯粹由「填了没填」决定。

**根因**

`prompt_{i}` 接的是 `VoiceClonePromptNode` / `LoadSpeakerNode`，返回
`List[VoiceClonePromptItem]`（单元素列表）。`unpack_role` 两个分支的归一化不一致：

| bank 形态 | 触发条件 | 旧返回值 | 每行复用它组成的 batch | 模型侧 `it.ref_code` |
|---|---|---|---|---|
| 裸 prompt（list） | `instruct_{i}` 为空 | `list[0]` = item | `[item, item]` ✅ | 正常 |
| `{"prompt": list, "instruct": ...}` | `instruct_{i}` 非空 | **整个 list** | `[[item], [item]]` ❌ | `'list' object has no attribute 'ref_code'` |

即带卡分支把列表原样返回，`DialogueInferenceNode` 再按行重复一次，
把 prompt 列表**嵌进**了批维度。`qwen_tts/inference/qwen3_tts_model.py:460`
的 `_prompt_items_to_voice_clone_prompt` 逐项取 `it.ref_code`，于是炸在 list 上。
所以 `instruct` 只是「走没走带卡分支」的开关，本身没有毒。

**决定**

`unpack_role` 抽出一个 `single()` 对内归一化，**两个分支统一返回单条 prompt**
（或打包 dict），不再返回列表。语义定为：role bank 里一个角色只有一个声音，
多余元素不会泄漏成批维度。

**影响**

- 填了声线卡的角色恢复正常合成，声线卡内容照旧进入 `instruct`。
- 边界：`{"prompt": [], ...}` 与裸 `[]` 均返回 `None`（此前裸 `[]` 已返回 None，
  带卡 `[]` 会返回 `[]`，同样会炸）。
- `tests/test_dialogue_markup.py` 新增 5 例回归（`UnpackRoleTests` 43 例总计）：
  带卡包装内的列表被拆包、裸/带卡返回值同形、多元素取首个、空列表为 `None`。
- 教训：只要两种入参形态汇入同一批处理路径，**归一化必须发生在解包处**，
  不能依赖下游「反正都是 prompt」的假设；下游按 `it.ref_code` 索引，
  对形状差异零容忍。

## 2026-10-26 · 非语言发声实测：`[laugh]` 类标签完全无效；笑/喊可用指令近似，哭与叹气较弱

**背景**

用户问能否合成笑声、哭声、喊声。代码里既没有对应预设（`EMOTION_PRESETS` 14 项全是情绪），
也没有发声类标签，需要实证哪些做法真的有效，而不是凭「`instruct` 接受任意自然语言」推断。

**方法**

远程 ComfyUI（`192.168.107.187:8188`，ROCm，RX 7900 XTX），1.7B Base +
`voices/柳如烟.wav` 音色克隆，`seed=42`、`temperature=0.9`、`batch_size=1`，
只改 `text` / `instruct`。共 22 个样本，两组提示词（温和 `[style:]` vs 强指令）。

**决定 / 结论**

1. **`[laugh]` / `[cry]` / `[喊]` 等标签完全无效，且不报错。**
   `[laugh]哈哈哈` 与 `哈哈哈` 的输出**逐采样完全相同**（`max|diff| = 0.0000`，
   SNR 176.9 dB）；作为对照，仅改 `instruct` 的差异是 −5.0 dB / LSD 9.2 dB。
   标签在 `parse_rich_text` 就被丢弃，控制台只有一行 dropped 警告。
2. **笑声可用强指令近似**：`"哈哈哈哈哈"` + `instruct="放声大笑，笑得停不下来，喘不上气"`
   的声谱图出现**规律性垂直断裂**（每个「哈」一脉冲），
   jitter 9.01%、shimmer 18.44%，显著高于对照组（jitter 4.44%、shimmer 13.77%）。
   英文 `hysterical laughter` 同样有效（jitter 6.80%、shimmer 18.05%）。
   纯拟声 `哈哈哈` 无指令时是**平滑连续**的谐波，属于「把字念出来」，不是笑。
3. **喊叫最容易**：`啊啊啊！！！！！！` 不加任何指令即出现强断裂与长元音，
   f0 达 381 Hz。`instruct` 只影响音色细节，不是必需项。
4. **哭声最弱**：`呜呜呜` + 强指令后 f0 降到 238 Hz、能量集中在 <1000 Hz 低频，
   上方为气声噪声，但**缺少真抽泣的断续/吸气结构**，听感更接近「哭腔念白」。
5. **叹气几乎不成立**：`"唉……"` + `instruct="长长地叹了一口气"` 仍带明显谐波，
   不是纯呼气噪声。
6. `[style:]` 的描述**确实到达模型**（`instruct` 非空时结果与空 `instruct` 不同），
   效果强弱取决于文案，与「标签是否被识别」是两件事。

**影响**

- 文档与回答中不得声称支持 `[laugh]` / `[cry]` 标签；当前行为是**静默丢弃**。
- 推荐写法：把拟声写进台词，并用 `instruct` / `[style:]` 描述发声方式；
  笑 > 喊 > 哭 > 叹气，按此顺序建立预期。
- 0.6B CustomVoice 丢弃 `instruct`，只剩「拟声文本」一条路，效果显著更弱。
- 以上均为声学指标 + 声谱图判断（本地无 GPU，无法试听），
  **最终验收仍需人耳**；`instruct` 是软约束这一定论（见 2026-10-24 条目）依然适用。
- 待办（未实施）：把 `[laugh]` 这类发声标签改为转 `style`，或至少把丢弃警告
  升级为明确提示「该标签不支持，请用 `[style:]` 或写进台词」。

## 2026-10-26 · ICL 参考音频不迁移表演；多角色共用一个音色时，声线卡无法制造音色区分

**背景**

正面回答「是否适合短剧配音」需要两块证据，此前都没有：

1. 短剧的关键痛点是**笑声/哭声**这类副语言表演，上一节已证明 `instruct` 只能近似。
   若 ICL（`x_vector_only=False`，参考音频 + 参考文本）能把表演一起迁移，
   那就还有一条路。
2. 短剧必然多角色。`RoleBank` 的 `instruct_{i}` 只能改「怎么说」，
   改不了「是谁」。需要确认它到底能拉开多少差异。

**方法**

同一远程环境，`seed=42`。第三轮把 S2（强指令笑声）与 S1（尖叫）作为
`LoadAudio` 参考分别跑 ICL 与 x_vector_only；第四轮跑一段 4 行 3 角色的短剧，
对比「有声线卡 / 裸 prompt / 声线卡 + 全局 instruct」。

**决定 / 结论**

1. **ICL 不迁移表演。** 以「放声大笑」样本为参考，`I1_icl_laugh` 的声谱图是
   正常念白的谐波带，参考音频那种规律脉冲条纹**完全没有出现**；
   `I2`（ICL + instruct）同样没有。x_vector_only（`I3`/`I4`）更只是音色克隆，
   与预期一致。
2. **ICL 会污染时长与节奏。** `I5`（以 1.12 s 尖叫为参考）把 7 个字念成 **2.78 s**，
   而同一句的中性基准是 1.52 s。参考音频越长、越异常，输出时长越离谱。
3. **多角色声线卡不能制造音色区分。** 三角色短剧（各角色接同一个 `柳如烟` 音色）
   六段话都落在同一说话人空间：声线卡版 f0 中位 375 Hz，裸 prompt 版 308 Hz，
   卡 + 全局 instruct 版 308 Hz。差异体现为**同一人的不同念法**，不是三个不同的人。
4. **对比全部落在同一音色上**（这是被测配置的固有限制，也是结论的关键前提）：
   音色由参考音频决定，声线卡只作用于 `instruct`。
   要做多角色，**必须每个角色各自准备音色**（`VoiceClonePrompt` / `LoadSpeaker`）。

**影响**

- 短剧配音的可用范围收窄为：**旁白 / 需要中性或单一情绪的长台词**
  可用；**多角色对手戏 + 强副语言表演**不可用，只能外部补齐。
- 不要用 ICL 参考音频去「带情绪」：表演不迁移，反而破坏时长。
- `docs` 与回答中不得声称「声线卡可区分角色音色」——它只改描述，不改音色。
- 结论的边界：本机无 GPU，全部判断基于声学指标与声谱图，**未做人耳验收**；
  且所有样本共用同一个女声参考，「多角色」一项只证明了「声线卡不产生区分」，
  不能反推「准备多个音色后仍无区分」。

## 2026-10-26 · 跨 seed 稳定性修正：笑声/喊声是**可靠**的（6/6），哭与叹气不可靠

**背景**

上一节关于副语言表演的结论来自 `seed=42` 的单个样本，无法回答「能不能用于生产」。
若笑只在个别 seed 偶发出现，那就不能用；必须测复现率。本条目**修正**上一节
「哭最弱」的表述——弱不等于随机，但上一节未区分二者。

**方法**

同一远程环境与音色，1.7B Base。5 类发声 × 6 个 seed（1/7/42/123/999/2026）= 30 个样本。
判定指标：`pulses`（响度包络上 ≥90 ms 间隔的爆发次数，笑声/喊声的客观标志）与 f0 抖动。

**依据**

| 用例 | 各 seed 的 pulses | ≥2 脉冲命中 | 时长范围 |
|---|---|---|---|
| `laugh_en`（hysterical laughter） | 4,4,4,4,4,4 | **6/6** | 0.96–1.36 s |
| `laugh_zh`（放声大笑…） | 2,5,4,4,5,5 | **6/6** | 1.12–1.59 s |
| `scream`（`啊啊啊！`，无 instruct） | 3,3,2,3,4,3 | **6/6** | 1.52–3.11 s |
| `cry_zh`（放声大哭…抽泣） | 1,3,1,1,1,1 | **1/6** | 1.20–1.67 s |
| `sigh`（长长地叹了一口气） | 1,1,1,1,1,1 | **0/6** | 0.64–1.28 s |

**决定 / 结论**

1. **笑声与喊声是可靠的**，不是 seed 偶然：英文笑声脉冲数在所有 6 个 seed 中
   恒为 4，中文笑声 4–5，说明「规律脉冲串」这一笑声核心特征稳定存在。
   两者可直接用于生产，只需挑文案与音色。
2. **哭声不可靠**：只有 1/6 的 seed 出现 ≥2 脉冲，其余是连续低频带
   （哭腔念白）。上一节「哭最弱」应细化为**情绪基调可给、抽泣事件不可控**。
3. **叹气在声学上成立但无事件结构**：6/6 都是单个连续气声段，
   谐波几乎消失、f0 跟踪抖动极大（抖动 55%/71%，说明周期结构已不可靠）。
   作为「呼气/叹气」使用是有效的，只是不能指望脉冲型断句。
4. 时长方差较大（喊声 1.52–3.11 s，2 倍差），逐句配音需按 seed 试听挑选。

**影响**

- 生产建议：笑/喊可以内建使用；哭只用情绪底色，**不要把抽泣当作可编排事件**；
  叹气仅当氛围音。
- 需要固定成品时，**按 seed 挑样**是可行手段（同一 seed 的可复现性已验证）。
- 待办（未实施）：把「笑/喊」正式纳入预设或标签体系（当前 `[laugh]` 仍被静默丢弃），
  并为它们加跨 seed 回归测试，避免以后改文案时悄悄退化。

## 2026-10-26 · 同 seed 完全确定性：同输入重跑得到**逐采样相同**的音频

**背景**

做副语言听感对照表时发现多组样本指标完全相同，需要确认是重复生成还是巧合。
这一点直接影响「能否按 seed 锁定成品」这一生产手段是否成立。

**依据**

60 个样本两两比对（长度差 ≤8 采样、逐采样计算 `max|diff|`），得到 6 对**完全相同**：

| 对 | max\|diff\| |
|---|---|
| `A1_laugh_raw` == `E1_laugh_tag` | 0.00e+00 |
| `S2_laugh_zh` == `laugh_zh_s42` | 0.00e+00 |
| `S3_cry_zh` == `cry_zh_s42` | 0.00e+00 |
| `S5_laugh_en` == `laugh_en_s42` | 0.00e+00 |
| `S7_sigh_zh` == `sigh_s42` | 0.00e+00 |
| `S8_scream_raw` == `scream_s42` | 0.00e+00 |

**决定 / 结论**

1. **同 seed + 同文本 + 同 instruct + 同模型 → 逐采样完全一致**（没有任何随机残差）。
   这不是 bug，是 `torch.manual_seed` + 确定性采样路径的预期行为。
2. 因此「按 seed 挑样并锁定」是**可靠的生产手段**，不是碰运气。
3. `A1 == E1` 这一对（`哈哈哈` vs `[laugh]哈哈哈`）同时是上一节
   「`[laugh]` 被静默丢弃」的**最强证据**——两者输入不同而输出逐采样相同。

**影响**

- 听感对照表里必须标注重复项，否则会让试听者重复劳动（已在
  `paralinguistic-ab.html` 中标注「与 #08 相同，可跳过」）。
- 跨 seed 的差异才是「真实的不确定性」；同一 seed 内的差异只可能来自
  代码/模型/参数变化，可作为**回归检测**：改代码后若同 seed 输出变了，
  说明行为发生了非预期变化。
- 待办（未实施）：可用「同 seed 输出哈希」作为副语言能力回归测试的基线。

## 2026-10-26 · 人耳验收推翻 `pulses` 判据：哭完全不存在；`aper` 才是有效指标

**背景**

此前三条结论都建立在声学代理指标上，从未经人耳。用户试听对照表后给出判断：
03（`S5_laugh_en`）「像冷笑」，05（`S2_laugh_zh`）「有点像是在笑」，
14/15/16/17（全部 `cry_zh_*`）「**完全是在读文本**」。

**决定 / 结论（推翻上一节）**

1. **`pulses` 不是副语言表演的判据，已废弃。** 14 的 pulses=3 只是「呜呜呜」
   被拆成三段念，而非抽泣。以 pulses ≥2 判定「1/6 seed 成功」是**伪成功**。
   上一节「哭只有 1/6 成功」应改为：**哭在 6/6 的 seed 上都不成立，从未成功**。
2. **`aper`（响度大时的不周期度）与听感一致**，可作替代指标：

   | 分组 | 用户判断 | aper 范围 |
   |---|---|---|
   | `cry_zh_*` 共 6 条 | 读文本 | 0.032 – 0.087 |
   | 笑声 3 条 | 冷笑 / 有点在笑 | 0.090 – 0.189 |
   | `Z0_control` | 普通念白 | 0.095 |

   念读的周期性明显更强（谐波清晰），真笑混入气声摩擦。
3. **笑声方向正确但强度不足**：05 只是「有点在笑」。加压实验（`L1`–`L5`）
   把 aper 推到 0.124–0.239，`L3`（笑得呛到）最高 0.239 —— **效果未知，待试听**。
4. **哭泣路线判定为不可行**：加压后的 `C1`（抽泣，气口全写进文本）aper=0.037，
   与读文本的 0.032–0.033 无法区分。唯一沾边的是 `C3`（哽咽**说台词**而非纯拟声，
   aper=0.137）——这说明**哭泣要靠「带词的哽咽」而非「呜呜声」**，且仍未经试听。
5. 指标与听感在**已听过的 8 个样本**上一致，但这不等于对未听样本也准；
   新样本必须重新试听验证。

**影响**

- 文档与回答中不得再用 `pulses` 论证表演存在；相关结论改为「待试听」。
- 哭泣：只保留「哽咽说台词」一条线索，其余（纯拟声、加重抽泣文案）判死。
- **教训**：声学代理指标只能用于**排序候选**，不能用于**判定效果成立**。
  此前三次「实测结论」中有一次（哭 1/6）是错的，根因是把「能量爆发」
  误当成「表演事件」。今后凡涉及听感，必须以人耳为准并写明「未经试听」。
- 对照表已升级为 v3（`docs` 同级产物 `paralinguistic-ab.html`），
  主指标换成 aper，并把用户判断逐条标注在表内。

## 2026-11-06 · 音色输入支持路径，`.qvp` 升为一等公民

**背景**

用户提出「音色输入支持按照路径吗」，并明确指出应该填的是 `.qvp` 路径。核查代码后确认
这是真实缺口，而非误解：

- `voice_store.AUDIO_EXTENSIONS` 不含 `.qvp`，下拉列表从不列出 `.qvp`；
- `LoadSpeakerNode.load_speaker` 解析出路径后直接 `librosa.load(path)`，`.qvp` 是
  `torch.save` 的二进制，必然抛异常；
- `.qvp` 只在 `sibling_metadata_paths()` 里被当作「音频旁边的隐式缓存」，
  从来不是可指定的输入；
- 其余节点只有 `AUDIO` / `VOICE_CLONE_PROMPT` 连线，无法按路径指定音色。

**决定**

1. **路径是一等输入**，参数名统一为 `ref_voice_path`（不叫 `ref_wav_path`，因为它同时接受
   `.qvp` 与音频）：`VoiceClone` / `EmotionalTTS` / `VoiceClonePrompt` 各加一个；
   `RoleBankNode` 加 `voice_path_1..8` 供 `DialogueInference` 按角色使用。
2. **路径非空即生效，忽略对应连线**，并打印 `ℹ️ ... ignoring the connected ...`。
   选「路径优先」而不是「连线优先」：路径是每次运行手动填的显式意图，
   而连线可能是从别的音色工作流复制过来的残留，静默沿用会让用户以为换了音色其实没换。
3. **`.qvp` 与音频是两条不同路径，不互相兜底**：
   - 指向 `.qvp` → `torch.load` 直接得到 prompt，不加载模型、不重编码；
   - 指向音频 → 解码后 `create_voice_clone_prompt`；
   - 指向音频且旁边有同名 `.qvp` → `LoadSpeaker` 仍读 `.qvp`（保持旧行为）；
   - 指向 `.qvp` 绝不会回落到同名音频，否则保存时的音色会被无声替换。
4. **裸名解析顺序 `.qvp` → 音频**，与第 3 条一致。
5. **缺 `ref_text` 时降级而非报错**：路径输入没有地方写参考文本，无同名 `.json` 时
   改用 `x_vector_only`（仅说话人向量）并打印提示。上游在 ICL 模式下会直接抛
   `ref_text is required`，对路径输入过于生硬；但必须提示，否则用户以为拿到了完整 ICL 质量。
6. **`VoiceClonePromptNode.ref_audio` 从 required 改为 optional**：只填路径时节点才可能执行。
   已连线的工作流行为不变。
7. `unpack_role()` 保持两返回值不变，新增 `role_voice_path()` 读取路径。
   `tests/test_dialogue_markup.py` 用 AST 抽取该函数并要求两元组，改签名会破坏测试契约。

**影响**

- `voice_store.py` 新增 `PROMPT_EXTENSIONS` / `VOICE_EXTENSIONS`、`VoiceSource`、
  `detect_source_kind()`、`describe_source()`、`resolve_voice_source()`。
- `nodes.py` 新增 `load_qvp_prompt()` / `load_audio_pair()` / `load_ref_voice()` /
  `prompt_from_audio_or_warn()` / `role_voice_path()`，五个节点共用同一套解析。
- 每个角色只在模型加载后解析一次路径；200 行脚本不会重复编码同一段参考音频。
- 单测 40 → 57（`test_voice_store.py`），另加 6 个 `RoleVoicePathTests`。
- **已知遗留（非本次引入）**：`tests/test_cuda_compatibility.py` 用空的假 `numpy` 模块加载
  `nodes.py`，而 `VoiceCloneNode._audio_tensor_to_tuple` 的 `np.ndarray` 注解在导入期求值，
  导致 14 个 error。HEAD 上同样存在，错误集合逐行 diff 一致。本次新增注解一律写成字符串形式，
  没有加重它，但该测试本身需要单独修（改 `from __future__ import annotations` 或补 stub）。

## 2026-11-06 · `.qvp` 打包自身 `ref_text` 与 `instruct`，成为音色的权威来源

**背景**

用户问「`.qvp` 有创建音色使用的提示词，为什么克隆还要加 `instruct`」。核查后确认前提不成立：

- `.qvp` 是 `VoiceClonePromptItem` 的序列化，字段只有
  `ref_code` / `ref_spk_embedding` / `x_vector_only_mode` / `icl_mode` / `ref_text`
  （`qwen_tts/inference/qwen3_tts_model.py:41-52`），**没有 `instruct`**；
- `SaveVoiceNode.save()` 只做 `torch.save(voice_clone_prompt, path_qvp)`，
  风格描述从未落盘；
- 两份 `ref_text` 来源不同：`.qvp` 里那份是 prompt 构建时用的转写（ICL 对齐用，
  `generate_icl_prompt`），`.json` 里那份是保存时手填的值，二者可以不一致。

用 `pickletools` 反汇编 `tests/data/柳如烟.qvp` 直接验证：`archive/data.pkl` 中
出现的是上述五字段（含 `ref_text`），`grep -a instruct` 无匹配。

2. **保存时以 `.qvp` 内嵌值为准**。`prompt_embedded_ref_text()` 从
   `VoiceClonePromptItem.ref_text` 取转写；手填的 `ref_text` 只在 prompt 没有转写时写入。
   **理由**：那份转写是模型实际条件过的文本，手填值无法追溯生效；若直接采用手填值，
   `.json` 会声称一个 prompt 从未见过的转写。两者不同时打印警告。
3. **`SaveVoice` 新增 `instruct` 输入**，写入 `.qvp` 与 `.json`。
4. **读取优先级统一**：`.qvp` 内嵌值 → 同名 `.json` → 空。
   `load_ref_voice()` 增加第 4 个返回值 `instruct`，`VoiceSource` 增加 `instruct` 字段。
5. **instruct 的回填语义是「填空」而非「覆盖」**：节点上显式填写优先，
   `.qvp` 里的声线卡只在节点为空时生效；`DialogueInference` 同理，
   `RoleBank` 的 `instruct_N` 优先于路径对应的卡。
   选这个方向是因为显式输入代表本次运行的意图，而卡是历史默认值。

**影响**

- `nodes.py`：新增 `read_qvp()` / `unpack_qvp()` / `load_qvp_bundle()` /
  `prompt_embedded_ref_text()` / `prompt_embedded_instruct()`；
  `load_qvp_prompt()` 保留为兼容包装。
- `voice_store.py`：`VoiceSource` 增加 `instruct`；`_read_ref_text` 改为 `_read_sidecar`
  返回二元组，新增 `_source()` 统一构造（4 处调用点）。
- **向后不兼容风险**：`.qvp` 由裸 prompt 变为 dict。本仓库的读取端（`unpack_qvp`）
  两种都能处理，但**更旧的 LoadSpeaker 构建读到新文件会拿到整个 dict 当 prompt**。
  版本号写进文件是为了将来能分辨；若确认不再需要兼容旧构建，可去掉这层顾虑。
- 单测 217 → 230，新增 `QvpPackagingTests`（13 项）覆盖：旧格式无文本、package 拆分、
  非字符串字段容错、内嵌转写提取（含批量歧义时返回空）、内嵌 instruct 仅来自 package、
  以及「内嵌优先于手填」的保存语义。
- 实测（`tests/data/柳如烟.qvp`）：旧格式解析出 `ref_text` 非空、`instruct` 为空；
  构造的新 package 能正确取回两者。

## 2026-11-06 · `.qvp` 的声线卡与手填 instruct 改为拼接（不覆盖）

**背景**

上一轮把 `.qvp` 的 `instruct` 做成「填空」语义（节点为空才生效）。用户要求改为**拼接**：
两者都要进入最终的 `instruct`。

**决定**

1. 新增 `merge_instruct(typed, voice_card)`，输出顺序固定为 **卡在前、手填在后**：

   ```text
   中高音区，音色清亮，这一句要压低声音
   ```

   - 卡在前：它是音色的基线（音区/音色/语速）；
   - 手填在后：本次运行的细化，放在最后（模型对靠后描述权重更高）；
   - 分隔符用全角「，」，与 `build_emotion_instruct` 一致。

2. **重叠不重复拼接**：`text == card`、`card in text`、`text in card` 三种情况直接返回较长的那个，
   避免「中高音区，中高音区」。这是最可能的误用（用户把卡又抄了一遍）。

3. 三个使用点统一：
   - `VoiceCloneNode`：`instruct = merge_instruct(instruct, path_instruct)`；
   - `EmotionalTTSNode`：同上，但**必须在 `build_segment_plans()` 之前**完成；
   - `DialogueInferenceNode`：`voice_card = merge_instruct(instruct_N, saved_card)`。

**影响**

- **修复一个上一轮引入的真 bug**：`EmotionalTTSNode` 原先在 `plans` 已构建之后才合并，
  而 `plans` 把 `instruct` 烘焙进每个 segment 的文本，所以合并结果**从未进入生成**。
  实测确认修复无效时两段文本都进不去、修复后都进得去。为此新增 `load_voice_card()`：
  只解析路径并读卡，不解码音频、不加载模型，供「模型之前就要用卡」的场景调用。
- **`merge_instruct` 不再引用模块级常量**：最初用 `VOICE_CARD_SEPARATOR`，但
  `tests/test_dialogue_markup.py` 通过 AST 抽取函数并只注入有限命名空间，
  常量不在其中，测试直接报 `NameError`。改为字面量。
  **教训**：`nodes.py` 里凡是需要被 AST 抽取测试的函数，不能依赖模块级名字。
- 单测 230 → 239，新增 `MergeInstructTests`（9 项）：单独卡、单独手填、两者拼接顺序、
  完全重复、互相包含、空白、双空、分隔符。
- 端到端实测：`build_segment_plans(parse_rich_text("第一句。[sad]第二句。"), extra_instruct=merge_instruct(...))`
  的两个 segment 均同时包含卡与手填文本，且情感预设仍在最前。
